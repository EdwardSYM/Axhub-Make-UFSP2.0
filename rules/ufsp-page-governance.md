# UFSP2.0 页面治理规范

> 状态：现行项目级页面治理规则，已纳入 `rules/README.md` 作为 UFSP2.0 新页面设计前的默认判断依据；具体样式仍按用户确认结果渐进沉淀。

## 1. 目标

本规范解决一个问题：以后在本项目里拿到新需求、截图或文档时，Codex 不再从零设计页面，也不再临时套通用 UI 风格，而是先按财会监督 V2.0 已沉淀页面的共性标准开始。

核心目标：

- 统一新页面启动流程。
- 区分设计语言、页面范式、组件规范和业务差异。
- 明确哪些文档、skill、主题、组件是默认依据。
- 明确哪些旧文件只作参考，避免规范冲突。
- 为后续抽取公共组件和建立项目专用 skill 做前置收敛。

## 2. 执行优先级

后续所有 UFSP2.0 新页面、页面优化、原型迭代，按以下优先级执行：

1. 用户本轮明确要求、截图、标注文档。
2. `AGENTS.md` 和 `rules/README.md` 中的项目级原则与任务分流。
3. 本文件：`rules/ufsp-page-governance.md`。
4. 已确认基线登记表：`rules/confirmed-baselines.md`。
5. 项目业务页面规范：`src/docs/业务页面设计规范.md`。
6. 同类已确认页面的 `index.tsx`、`style.css`、`spec.md`。
7. 当前页面自己的 `spec.md`。
8. 通用设计 skill 或通用 UI 经验。

若第 2-8 项冲突，按优先级高者执行。通用 skill 只能辅助判断，不得覆盖项目已确认页面样式。

同一类组件存在多个实现口径时，在用户没有给出更新确认的前提下，优先采用项目中真实复用最多、覆盖页面最广的公共组件或稳定实现。例如全局顶栏以公共 `TopBar` 为唯一基准，单页顶栏、旧 HTML 顶栏和示例组件不得覆盖。复用次数不能覆盖用户最新明确确认。

## 3. 新页面启动流程

收到新需求后，不直接写页面。先完成以下判断：

1. 判断页面类型。
2. 选择参考页面。
3. 判断参考页面可信度。
4. 读取参考页面代码和规格。
5. 识别已确认基线、冻结区和可变区。
6. 评估本次需求变更影响范围。
7. 映射页面结构。
8. 确定可复用组件或样式。
9. 编写或更新 `spec.md`。
10. 实现静态原型。
11. 做与风险匹配的验收。

如果用户只要求方案或治理分析，不进入代码实现。

## 3.1 已确认基线登记

项目内已确认的页面样式、组件规范和交互状态，应当登记为基线。后续新需求不得默认覆盖已确认基线。

基线状态分三类：

- 强基线：用户已明确确认，可作为同类页面默认复用依据。
- 局部基线：用户只确认了某个局部组件或局部结构，只能在该范围内复用。
- 待确认：页面仍在调整或存在明显争议，不得作为覆盖其他页面的依据。

基线登记至少包含：

- 页面或组件名称。
- 文件路径。
- 已确认范围。
- 未确认范围。
- 适用页面类型。
- 不能被覆盖的冻结项。

登记表位置：`rules/confirmed-baselines.md`。

如果登记表尚未覆盖当前页面或组件，执行者也必须在改动前根据最近对话和当前页面状态临时判断，并在最终说明里标明“本次保护了哪些已确认样式”。用户确认后，应提醒是否补充登记表。

## 3.2 需求变更影响评估

每次需求调整前，先判断影响范围：

- A 类：只改业务内容，例如字段、文案、mock 数据、状态数量。
- B 类：改业务交互，例如按钮显隐、点击后反馈、筛选条件。
- C 类：改页面结构，例如新增区域、调整信息分组、变更页面流程。
- D 类：改组件规范，例如按钮、输入框、表格、菜单、业务树、分页、弹窗、抽屉样式。

处理规则：

- A/B 类可以在冻结样式上直接改。
- C 类必须说明会不会影响已确认布局骨架。
- D 类必须暂停并让用户确认。

不得把 A/B/C 类需求当成 D 类处理。也就是说，改字段、改流程、改业务方案，不等于可以改组件样式。

## 3.3 冻结区与可变区

实现或调整前，必须区分：

- 冻结区：已确认组件规范、页面骨架、菜单、业务树、按钮、输入框、表格、分页、页签、表单页头、弹窗、抽屉等。
- 可变区：本次需求指定的字段、文案、数据、业务状态、按钮显隐、业务动作、局部内容组织。

默认规则：

- 先保护冻结区，再处理可变区。
- 如果可变区无法实现，需要动冻结区，必须先说明原因和替代方案。
- 新增业务内容应优先嵌入现有骨架，不得借新增内容重写骨架。

## 3.4 渐进视觉校准与积累

页面标准默认采用“先复用、边迭代、边沉淀”的方式，不要求用户逐项确认字号、宽度、颜色、间距等参数，也不要求在新页面前一次性完成全局样式统一。

默认流程：

1. 执行者先从强基准、公共组件和复用最多的稳定实现中提取候选基线。
2. 当前页面先按既有组件和已确认页面实现，不因为统一样式治理而延误业务需求。
3. 用户在具体页面中指出不符合预期的位置时，执行者判断它属于当前页局部、页面范式还是组件规范。
4. 被明确确认的口径再写入基线登记、页面规格、规则文档，必要时再沉淀到主题变量或公共组件。
5. 后续需求变化只允许调整业务可变区，不得带动已确认组件样式回退。

可运行视觉样板仍可使用，但只作为以下场景的辅助工具：

- 同一类页面或组件已经反复出现偏差。
- 文字描述容易引起歧义，需要通过整屏样张确认。
- 准备抽公共组件、页面模板或主题变量前，需要集中验证视觉效果。

以下内容不逐项询问，默认按既有强基准执行：

- 已由公共组件承载且复用稳定的样式。
- 多个已确认页面一致使用的尺寸、密度、颜色和状态。
- 明显错误修正，例如原生粗蓝聚焦框、菜单层级错位、控件字号异常。

只有以下情况需要单独确认：

- 两个强基准存在无法自动消解的冲突。
- 现有组件无法满足核心业务，需要新增组件或组件变体。
- 调整会覆盖其他已确认页面的冻结区。
- 新页面类型、关键交互或业务流程没有现成范式。

## 4. 页面类型

### 4.1 首页类

适用场景：

- 系统总入口。
- 模块分发。
- 全局概览。
- 公共协同。
- 基础支撑入口。

默认参考：

- `src/prototypes/fiscal-supervision-home2`

设计要点：

- 使用 1920 宽工作台口径。
- 内容区铺满页面主体，不做窄版居中卡片。
- 模块以轻卡片承载，但避免营销页式大 hero。
- 信息职责是分发、概览、提醒，不承载完整业务闭环。

### 4.2 工作台类

适用场景：

- 专项监督工作台。
- 日常监督工作台。
- 单个主题的办理、分析、趋势、任务聚合。

默认参考：

- `src/prototypes/topic-workbench2`
- `src/prototypes/richang-yewu-workbench`
- `src/prototypes/richang-zhuanti-workbench`
- `src/prototypes/supervisor-workbench`
- `src/prototypes/supervised-workbench`

设计要点：

- 和首页共享财会监督 V2.0 设计语言。
- 允许轻卡片和分组面板，但不能做落地页式装饰。
- 强调任务路径、业务状态、分析入口和继续办理。
- 组件密度可略低于列表页，但仍保持中后台效率感。

### 4.3 业务列表页

适用场景：

- 问题库。
- 案例库。
- 考评库。
- 提示词版本管理。
- 其他含页签、菜单、业务树、查询、表格、分页的页面。

默认参考：

- `src/prototypes/problem-library-function-list`
- `src/prototypes/case-library-ai`
- `src/prototypes/evaluation-assessment`

设计要点：

- 默认 1920 x 1080、浏览器 100% 缩放作为主验收口径。
- 优先复用三段式结构：系统菜单、业务树或目录、列表/表格工作区。
- 页签、工具栏、查询、表格、分页使用 32px/48px/56px 的既有密度。
- 行操作只保留一个主操作，其余收纳到更多操作。
- 不新增重复标题块、说明块、指标卡，除非业务确实需要。

### 4.4 表单 / 新增 / 编辑页

适用场景：

- 新增。
- 编辑。
- 申请。

默认参考：

- `src/prototypes/case-library-ai` 的新增、申请、审核页。
- `src/prototypes/problem-library-function-list` 的表单页。

设计要点：

- 顶部使用 64px 表单页头。
- 左侧为圆形返回按钮。
- 标题格式使用“功能名称 / 新增或编辑对象”。
- 正文使用蓝色竖线分节标题。
- 输入框、下拉、文本域保持项目标准控件样式，不出现浏览器原生粗蓝框。

### 4.4.1 详情 / 阅读 / 核验页

适用场景：

- 单据、案例、问题和文书详情。
- 原文阅读、命中定位、来源追溯。
- 以核验和理解为主、录入操作为辅的全页面工作区。

设计要点：

- 顶部仍可使用 64px 白色操作栏和圆形返回按钮，但标题只表达当前页面身份，使用最短且不歧义的名称；模块位置已由系统菜单表达时，不重复写成长面包屑。
- 页面级动作集中在页头；案例标题、文号、类型、状态等对象身份信息集中在摘要或正文首区表达一次。
- 详情阅读页不直接套用新增编辑页的蓝色竖线分节标题。先判断内容是同组信息、相邻分组、业务阶段还是独立载体，再选择留白、浅底、局部分隔或载体边界。
- 连续阅读任务优先使用一体化白色工作区；文书纸张、附件预览等确有独立载体语义的内容可保留自身边界。

### 4.5 抽屉 / 弹窗

适用场景：

- 抽屉：复杂录入、规则维护、详情补充、侧向编辑。
- 弹窗：确认、轻量选择、低复杂度创建。

默认参考：

- 案例库抽屉与弹窗。
- 问题库抽屉与弹窗。
- 提示词规则抽屉。

设计要点：

- 抽屉用于持续编辑；弹窗用于确认和轻量选择。
- 弹窗不承载复杂表单。
- 危险操作必须二次确认。
- 弹窗按钮顺序、尺寸、颜色跟随 `ufsp-btn`。

## 5. 统一设计语言

UFSP2.0 的默认设计语言不是通用“高级感”模板，而是政务财会监督中后台：

- 克制、专业、可靠。
- 高密度但不拥挤。
- 弱边界、轻阴影、低饱和蓝灰。
- 业务内容默认信息层级优先、边界克制：先判断区块关系，再在留白、文字层级、浅底分组、局部分隔和完整边界中选择最合适的方式；不以“线越少”或“卡片越少”作为单独目标。
- 清晰层级，少装饰。
- 组件可扫描，适合重复业务操作。

默认视觉口径：

- 顶栏深蓝渐变来自现有 `TopBar`。
- 页面主体以 `#F5F8FF` 或浅蓝灰作为外部画布。
- 业务模块内部以白色面板为主。
- 主操作蓝使用项目已确认的蓝色体系。
- 表头使用蓝灰强调色。
- 文本主色、次色、辅助色使用 rgba 黑色层级。
- 圆角保持克制并统一：控件 4px，业务面板和业务卡片统一 8px，同一页面不得混用 8px、12px、16px；胶囊搜索框、圆形返回按钮、头像等明确形态组件除外。

设计时允许“无厚重边框、弱边界、高级克制”，但不得脱离当前项目：

- 不使用营销页大标题。
- 不使用大面积渐变装饰。
- 不使用过大圆角和厚重投影。
- 不使用孤立卡片堆叠替代表格和表单。

## 6. 组件规范基线

当前项目已有样式沉淀，但还没有全部组件化。新页面应先复用已有 class 或参考已有页面代码，不要临时重写。

### 6.1 组件复用优先原则

新需求匹配已有组件或已确认样式时，必须优先复用现成组件和现成规范。

执行顺序：

1. 先判断需求属于哪类组件或页面范式。
2. 再查找项目里是否已有同类组件、同类样式或已确认页面实现。
3. 如果已有组件能满足需求，直接复用，不新增设计。
4. 如果已有组件只能部分满足，优先用业务内容、布局组合或局部参数解决。
5. 只有现有组件确实无法满足核心需求时，才考虑新增组件或新增设计。
6. 新增组件或新增设计前，必须向用户说明原因、影响范围和替代方案，并等待用户确认。

判断口径：

- “看起来可以重新设计”不等于需要新增组件。
- “新需求”不等于“新样式”。
- “页面不同”不等于“组件规范可以不同”。
- 只有需求目标无法通过现有组件组合达成时，才进入新增设计。

### 6.2 组件规范冻结原则

组件规范类样式属于冻结基线。只要某一类组件样式已经被用户确认，后续任何需求调整都不得默认改动它。

冻结范围包括：

- 组件尺寸：高度、宽度、内边距、间距、圆角。
- 组件排版：字号、字重、行高、图标尺寸、图文间距。
- 组件状态：默认、悬停、选中、聚焦、禁用、危险、展开、折叠。
- 组件结构：系统菜单、业务树、页签、工具栏、表格、分页、表单页头、输入框、抽屉、弹窗。
- 组件视觉：颜色、边框、阴影、背景、分隔线、状态标识。

需求变更默认只能修改：

- 业务字段。
- 业务文案。
- mock 数据。
- 数据状态。
- 业务流程。
- 按钮是否出现、是否可点、触发什么业务反馈。

需求变更不得顺手修改：

- 已确认的按钮样式。
- 已确认的输入框样式。
- 已确认的表格密度。
- 已确认的菜单和业务树样式。
- 已确认的页签、分页、弹窗、抽屉样式。

如果新需求确实需要调整组件规范，必须先暂停并向用户说明：

- 影响哪个已确认组件。
- 为什么业务需求会影响组件规范。
- 是否有不改组件样式的替代方案。
- 等用户明确确认后再改。

判断口径：

- “改功能 / 改字段 / 改流程”不等于可以改组件样式。
- “新增页面内容”不等于可以重写页面骨架。
- “参考其他页面”不等于可以覆盖当前页面已确认样式。
- “优化页面”也必须先区分冻结区和可变区。

### 6.3 组件契约

复用组件时，必须区分“可变参数”和“不可变规范”。

允许变化：

- 数据内容。
- 展示文案。
- 是否展示。
- 是否禁用。
- 操作回调。
- 业务状态值。
- 列表字段组合。

不允许默认变化：

- 控件高度。
- 字号和字重。
- 图标尺寸。
- 图文间距。
- 圆角。
- 边框。
- 阴影。
- 默认 / 悬停 / 聚焦 / 选中 / 禁用状态样式。
- 表格行高、表头高度、分页尺寸。

如果确实需要改变不可变规范，应当视为“新增组件规范”或“调整组件规范”，先提交原因和方案给用户确认。

## 7. 禁止项

以下规则用于避免再次出现页面样式偏离：

- 禁止在新页面根节点写通用控件覆盖，例如 `.xxx-page button`、`.xxx-page input`、`.xxx-page select`、`.xxx-page textarea`。
- 禁止在新页面根节点覆盖 `table`、`thead`、`tbody`、`tr`、`th`、`td` 的通用样式。
- 禁止使用 `font` 简写覆盖控件字体；如确需继承，只能使用 `font-family: inherit`。
- 禁止给输入框加浏览器原生蓝色粗 outline。
- 禁止用页面级 `button { border: 0 }` 破坏标准按钮边框和阴影。
- 禁止用页面级 `outline`、`box-shadow`、`border` 重置覆盖标准控件状态。
- 禁止重定义已确认 `ufsp-*` class 的核心尺寸、字号、边框、阴影和状态样式。
- 禁止重新实现顶部系统导航。
- 禁止重新发明系统菜单、业务树、表格、分页、表单页头。
- 禁止把首页/工作台的卡片风格直接搬到业务列表页。
- 禁止把业务列表页做成大卡片堆叠。
- 禁止未经用户确认新增真实接口、数据库、权限、复杂校验或真实业务公式。
- 禁止引入新的 UI 库。
- 禁止只根据 PRD 字面搭结构而不参考已确认页面。

## 8. 文件路径职责

目录和规则文件的唯一职责统一在 `rules/README.md` 中维护，本文件不再保存第二份目录盘点。

页面治理只使用以下执行关系：

- `.agents/skills/` 中的 skill 只能辅助执行，不能覆盖本文件和已确认基线。
- `src/themes/antd-new` 提供主题语义和 token，不能覆盖已确认业务页面样式。
- `src/docs/业务页面设计规范.md` 提供业务页视觉与组件规范。
- `src/prototypes/` 承载页面，`src/components/` 和 `src/common/components/` 承载可复用组件。
- 新页面和组件不得写入旧的 `src/pages/`、`src/elements/`。

## 9. 参考页面选择规则

新页面必须选择至少一个主参考页面：

| 页面需求 | 主参考 | 辅助参考 |
| --- | --- | --- |
| 首页 / 总览入口 | `fiscal-supervision-home2` | `global-overview-2` |
| 专项 / 日常工作台 | `topic-workbench2`、`richang-yewu-workbench`、`richang-zhuanti-workbench` | `supervisor-workbench`、`supervised-workbench` |
| 有系统菜单的业务列表 | `case-library-ai` | `problem-library-function-list`、`evaluation-assessment` |
| 有业务树的列表 | `problem-library-function-list` | `case-library-ai` |
| 申请 / 审核表单 | `case-library-ai` | `typical-case-application`、`typical-case-review` |
| 普通表单编辑 | `case-library-ai` | `problem-library-function-list` |
| 抽屉维护 | `case-library-ai` | `problem-library-function-list` |
| 规则配置类页面 | 暂无强基准 | `case-library-ai` 的表单组件、旧 HTML 的配置业务语义；使用前需确认新增变体 |

如果参考页面本身存在未确认或明显偏差，必须在实现前说明，并选择更稳定的同类页面作为主参考。

### 9.1 参考页面可信度分级

参考页面使用前必须判断可信度：

- 强基准：页面或对应组件已被用户明确确认，可直接作为同类页面规范来源。
- 局部基准：仅某些组件或区域被确认，只能复用这些已确认部分。
- 待确认参考：页面仍在调整或用户明确指出过问题，只能用于理解业务，不得覆盖强基准。
- 反例：用户指出过“不符合规范”的效果，应登记为禁止复用的反例。

使用规则：

- 强基准优先于局部基准。
- 局部基准只能在确认范围内使用。
- 待确认参考不得改变已确认组件规范。
- 同一页面内，当前用户已确认的样式优先于其他页面参考样式。

## 10. 页面实现前检查清单

设计或实现前，必须完成：

- 已判断页面类型。
- 已选择主参考页面和辅助参考页面。
- 已查阅 `rules/confirmed-baselines.md`。
- 已判断参考页面可信度。
- 已识别已确认基线。
- 已区分冻结区和可变区。
- 已评估需求变更影响类型。
- 已读取参考页面的 `index.tsx`、`style.css`、`spec.md`。
- 已确认是否需要系统菜单、业务树、页签、工具栏、表格、分页、表单、抽屉。
- 已写入或更新当前页面 `spec.md`。
- 已确认只使用本地 mock 数据。
- 已确认不接接口、不做权限、不做真实公式、不加复杂校验。
- 已确认没有新增通用控件覆盖规则。

## 11. 验收口径

默认视觉口径：

- 桌面主口径：1920 x 1080。
- 浏览器缩放：100%。
- 顶部 TopBar：按现有公共组件实际高度 64px。
- 控件：32px 高。
- 表头 / 表格行：优先 32px。
- 表单页头：64px。
- 页面主体：最大 1920px 居中，更宽画布只自然留白。

验收方式按任务风险选择：

- 文档治理：轻量阅读自查即可。
- 小范围静态原型：读取变更文件自查，必要时运行页面验收。
- 新建复杂原型：按项目要求运行 `check-app-ready.mjs`，并视情况做浏览器视觉检查。

若用户明确要求不运行构建、浏览器或验收脚本，则按用户要求执行，并在最终说明未运行。

## 12. 已确认样式的同步策略

当用户确认某个位置的最新样式调整后，不默认全项目同步，也不默认只保留在当前页面。必须先判断该调整属于哪一类。

### 12.1 同步判断

确认后的样式调整分四类：

- 必须同步：组件规范类调整，例如按钮、输入框、表格、分页、页签、系统菜单、业务树、弹窗、抽屉的尺寸、字号、状态、颜色、间距。
- 应该同步：明显错误修正，例如浏览器原生 focus 粗蓝框、按钮字号异常、表格密度错误、菜单层级错误、业务树位置错误。
- 可选同步：页面范式类优化，例如列表页工具栏组织、表单页头信息密度、工作台卡片分组方式。需看同类页面是否适用。
- 不应同步：当前业务独有内容，例如字段分组、业务文案、mock 数据、局部流程、特定页面的信息组织。

### 12.2 同步前检查

执行同步前必须检查：

1. 这次确认的是组件规范、页面范式，还是业务局部方案。
2. 哪些页面使用了同类组件或同类结构。
3. 这些页面是否已经被用户确认过。
4. 是否会覆盖某个已确认页面的冻结区。
5. 是否存在业务差异，需要保留变体。

如果会覆盖另一个已确认页面的冻结区，不能直接同步，必须先说明冲突点并让用户确认。

### 12.3 同步方式

根据影响范围选择同步方式：

- 小范围错误修正：可以直接修同类页面，并在最终说明修了哪些同类问题。
- 组件规范更新：先登记为新基线，再同步同类页面；如果影响面较大，优先抽公共 class 或公共组件。
- 页面范式优化：先用于当前页面和后续新页面，旧页面是否同步由用户确认。
- 业务局部调整：只改当前页面，不扩散。

### 12.4 冲突处理

如果新确认样式和旧页面已确认样式不一致，按以下顺序处理：

1. 判断是否其实是不同场景下的组件变体。
2. 如果是变体，登记适用条件，不互相覆盖。
3. 如果不是变体，列出现有 A/B 两种样式和影响页面。
4. 由用户确认哪一个升级为全局基线。
5. 确认前，不做跨页面覆盖。

### 12.5 默认原则

- 新确认样式不等于自动覆盖所有旧页面。
- 已确认组件规范应尽量同步，避免同类页面反复返工。
- 已确认页面冻结区不能被另一个页面的需求变更顺手改掉。
- 同步前先识别范围，同步后要说明影响面。
- 长期解决方式是把高频同步项组件化，而不是反复复制页面 CSS。

## 13. 规范迭代与互动机制

本文件不是一次性定死的规范，而是 UFSP2.0 页面持续沉淀的治理入口。后续如果出现新的问题、新页面类型、新组件场景或反复调整点，执行者必须主动判断是否需要更新本文件。

### 13.1 触发更新的场景

出现以下情况时，必须提醒用户是否更新本文件：

- 用户连续指出同一类样式问题，例如字号、按钮、输入框、表格密度、业务树、菜单层级。
- 新需求暴露了现有规范未覆盖的组件或页面形态。
- 同一类页面在不同原型里出现了两种以上实现方式。
- 某个页面被用户明确确认，可升级为强基准。
- 某个页面或局部效果被用户明确指出为反例。
- 需求变更过程中发现已确认组件样式被误改。
- 当前规则、skill、主题、文档之间出现冲突或优先级不清。

### 13.2 与用户互动的默认方式

遇到可沉淀的问题时，默认先服务当前页面需求，再把已确认口径逐步沉淀，不把内部设计参数逐条交给用户审批：

1. 执行者先完成必要证据盘点，自动继承强基准和复用最多的稳定实现。
2. 当前需求能通过已有组件和页面范式解决时，直接实现当前页，不额外发起全局统一。
3. 用户确认某个局部样式后，执行者判断是否需要登记为基线、同步同类页面或抽公共组件。
4. 只有反复偏差、组件化前校准或文字难以说明时，才制作视觉样板集中确认。
5. 最终说明只列需要用户决定的冲突、新增项和影响范围，不重复罗列所有已继承参数。

只有问题会直接改变页面范式、组件契约、其他已确认页面冻结区或新增公共组件时，才在实现前暂停并询问用户。

### 13.2.1 计划闭环与回顾检查

页面治理任务经常会拆成“规则入口、基线登记、组件化、旧文件清理、记忆沉淀”等多个子项。执行者完成其中一项后，必须回到完整计划检查剩余事项，不能把子项完成误判为任务完成。

默认检查顺序：

1. 用户最初要解决的问题是什么。
2. 本轮显式或隐式形成了哪些待办。
3. 已完成的是哪一项，是否只是整体计划的一部分。
4. 是否还有重复文件、旧规范引用、冲突组件、未登记基线、未同步 `spec.md` 或需用户确认的治理项。
5. 如果剩余项不适合当前继续做，必须说明原因和建议时机。

凡是用户要求“检查还有没有”“回顾”“总结原因”“沉淀方案”，最终说明必须包含这个回顾结果。

### 13.3 规范更新分级

规范更新分三类处理：

- 轻量补充：补充禁止项、检查项、已确认口径，可直接提出并等待用户确认后追加。
- 结构调整：调整章节、优先级、页面分类、执行流程，必须先说明影响范围。
- 组件规范变更：涉及按钮、输入框、表格、菜单、业务树、弹窗等组件契约，必须先列出现有样式、变更原因、替代方案，再由用户确认。

### 13.4 持续优化的产物

后续根据用户确认，逐步形成四类产物：

- 规则入口：`rules/README.md`，维护任务分流和每份规则的唯一职责。
- 页面治理：本文件，统一新页面启动、页面类型、基准页、冻结区和可变区。
- 组件规范：把已确认组件契约从页面 CSS 中抽取出来。
- 项目 skill：把稳定执行流程沉淀为 UFSP2.0 专用页面设计 / 实现 skill。

任何产物更新都应保持一个原则：先保护已确认样式，再吸收新场景。
