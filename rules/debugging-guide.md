# 调试与验收失败处理

本文件只在页面已经出现构建、运行、交互或样式错误时使用。普通静态原型小改不自动进入完整调试流程。

## 1. 基本原则

- 用户不需要执行命令或提供技术术语，由 Agent 主动收集证据。
- 先读取 `rules/README.md`、`development-guide.md` 和当前页面 `spec.md`。
- 一次定位一个根因，使用最小修改修复，不顺手重构无关代码。
- 调试不能改变已确认页面骨架和组件样式；样式问题先对照基线和同类页面。
- 先使用项目现有依赖、组件和实现，不因报错切换技术栈或新增库。

## 2. 证据收集

根据问题类型获取最小充分证据：

1. 读取当前页面及相关组件代码。
2. 查看验收脚本或开发终端中的直接错误。
3. 页面可以打开时，按需检查页面状态、浏览器错误、交互结果或截图。
4. 对照当前页面 `spec.md`、用户截图和已确认基线判断预期结果。

不得在没有证据时反复试改样式或同时修改多个可疑位置。

## 3. 问题分类

### 3.1 构建错误

- 检查 TypeScript、语法、导入路径和缺失依赖。
- 优先修正当前改动引入的问题。
- 新增依赖前确认项目中没有现成替代。

### 3.2 运行时错误

- 根据错误位置检查空值、数据结构、异步状态和组件接口。
- 保持 mock 数据结构与 `spec.md` 一致。
- 不用大范围兜底掩盖真实数据契约问题。

### 3.3 交互错误

- 明确触发动作、预期反馈和状态变化。
- 检查当前页面局部逻辑，不擅自扩展完整生产流程。
- 业务流程不清且会影响验收时，再向用户确认。

### 3.4 样式错误

- 先判断是当前页局部、页面范式、组件规范还是明显错误。
- 检查是否存在页面级 `button`、`input`、`table` 等通用覆盖。
- 检查字号、控件高度、间距、聚焦态和表格密度是否偏离已确认基线。
- 修复明显错误时保持业务内容和交互不变。

## 4. 修复与验证

1. 说明或记录已确认的根因。
2. 修改最小相关文件。
3. 按问题风险选择验证：
   - 文案、注释或规则引用：文件自查。
   - 局部静态样式：结构和样式自查，必要时查看页面。
   - 构建、运行或复杂交互：运行对应页面验收。
4. 若问题仍存在，重新收集新证据，不重复同一无效修改。

需要页面验收时，使用：

```bash
node scripts/check-app-ready.mjs /components/[组件目录]
# 或
node scripts/check-app-ready.mjs /prototypes/[原型目录]
```

## 5. 收口检查

- [ ] 已定位并修复根因，而不是只遮盖表现。
- [ ] 没有修改无关页面或已确认冻结样式。
- [ ] 代码与当前页面 `spec.md` 保持一致。
- [ ] 没有新增旧目录、失效引用或不必要依赖。
- [ ] 已完成与风险匹配的验证，并说明未执行的重型检查。
