# 需求对齐规则

本文件只在关键条件缺失时使用。目标是补齐会影响范围、流程、页面结构、数据来源、技术路线或验收结果的信息，不是让用户逐项审批设计参数。

## 1. 何时需要对齐

出现以下情况之一时启动：

- 用户明确要求先分析、讨论或确认方案。
- 页面目标、使用角色或核心任务不清。
- 缺少的信息会改变页面结构、业务流程或实现范围。
- 两个现有基线或参考页面存在冲突。
- 现有组件无法满足核心业务，可能需要新组件或新变体。
- 数据来源、关键状态或验收标准无法从资料和现有页面判断。

以下情况不启动完整对齐：

- 小范围、明确、低风险的字段、文案、mock 数据或局部样式修正。
- 已有强基准、同类页面和 `spec.md` 足以确定实现。
- 缺失信息只影响不重要的展示细节，可以按项目稳定口径合理假设。

## 2. 提问前检查

1. 完整阅读用户提供的文档、截图、标注和链接内容。
2. 阅读当前页面及同类已确认页面的 `spec.md`、代码和基线登记。
3. 区分哪些信息已经明确、哪些可以沿用现有规范、哪些必须由用户决定。
4. 只询问会真实改变方案或验收结果的问题。

不得重复询问资料中已经说明的内容，也不得把字号、颜色、间距等已有组件参数逐项交给用户确认。

## 3. 最小确认范围

按当前任务需要选择，不要求每次全部确认：

### 3.1 目标与范围

- 页面或功能要解决什么问题。
- 主要使用角色和关键任务。
- 本轮只做方案、静态原型还是完整实现。
- 明确不在本轮处理的内容。

### 3.2 页面与流程

- 页面类型以及是否已有同类基准。
- 关键操作、状态变化和完成条件。
- 是否需要列表、表单、业务树、抽屉、弹窗等已有范式。
- 新需求是否会影响已确认页面骨架或组件契约。

### 3.3 数据与验收

- 展示所需的关键字段和数据来源。
- 必须覆盖的空态、禁用态、异常态或权限差异。
- 用户判断“完成”的核心标准。
- 只有明确涉及 Axure API 或可复用平台组件时，才确认事件、动作、变量和配置项。

## 4. 沟通方式

- 优先提出一个最关键问题，不一次堆出长清单。
- 存在多条路线时给出 2-3 个选项，说明推荐项、适用场景和工作量差异。
- 可合理假设的细节直接按项目基线处理，并在结果中简要说明。
- 新组件、新变体或跨页面同步必须说明原因、影响范围和不改组件的替代方案。
- 用户回答后立即收敛方案，不重复确认已经确定的内容。

## 5. 结束条件

满足以下条件即可结束对齐并进入设计或实现：

- 核心目标和本轮范围明确。
- 页面骨架和主要业务流程可判断。
- 关键数据和状态足够支撑静态原型。
- 已识别冻结区、可变区和可能冲突的基线。
- 验收结果可以被清楚描述。
