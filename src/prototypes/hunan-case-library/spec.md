### 字段与目录

- 主体类型：单位、个人。单位类型内置行政事业单位、会计师事务所、资产评估机构、代理记账机构、国有企业、一般企业、政府采购采购人/供应商/代理机构。个人类型内置注册会计师、资产评估师、政府采购评审专家、其他人员。
- 单位/个人类型、文书类型、处理类型、处罚类型由共享元数据与标签目录供给，入库页不再独立维护另一套选项；主体类型固定。
- “供应商或代理机构”“涉及政府采购采购人”等源表不一致值不能擅自认定成精确类型；后续通过别名归并或候选确认。
- `inspection_year`、`inspection_name`、`subject_kind`、`unit_type`、`person_type`、`penalty_type` 为新增字段。`handling_method` 对应处理类型，`penalty_type` 对应处罚类型；措施类别决定当前条目使用哪个目录。
- 四列栅格中监督领域、方面、问题类型、问题性质各占一列；单位名称可跨两列，事实正文整行。规则同步到页面治理规范。
- 罚款、没收违法所得各自记录，源表“罚没金额合计”“其中因会计法罚款”不是新的处罚类型，也不能重复累计。本轮不实现真实汇总公式。
- 处罚阶次仅保留原文明示值，不由问题性质推算。

### 建议值到入库的操作

1. 正式选择控件只显示已采用值。未匹配的原始提炼结果在字段下显示“未采用”，保存草稿不将建议变成正式标签。
2. 可扩展目录：选择已有标签，或打开“确认标签建议”，比较已有值并完善定义、原文依据；确认新增后标签生效并回填字段。仅保存建议则留在标签管理待处理。
3. 固定目录：可选择已有参考值；不匹配时提交目录建议到元数据反馈，不允许一键自由新增标准。湖南标准待确认期间参考分类可后补，不推测问题性质。
4. 标签生效不等于案例入库；用户仍须“校验并入库”。已入库数据仍通过草稿修正、校验和新版本更新，不能被候选值静默覆盖。
5. 非处罚文书切换后若仍有原处罚措施，保留内容并提示核对，不静默删除；告知书所有处罚措施标为拟处罚。

### 演示与实现边界

- 本地保留原有多问题案例与个人案例，补充统计表“2026”页第 5、35 行两条来源样例。
- 两条样例均为 2026 年发文、2025 年检查。统计表缺少完整标题、问题事实和引用依据，保持未入库，不伪造事实。
- 原始统计表不修改，未做真实批量导入、解析、LLM匹配、权限或知识库写入。本轮只是共享本地数据和页面交互。
- 待客户确认：一案主体的完整边界；湖南标准与统计字段映射；混合单位分类的归并；无具体问题的通知/请示是否作为案例还是资料管理。
- 最终 Word/生产实现方案仍在各页面确认后整理。

## 1. 页面定位

本原型用于湖南场景的案例库功能演示。当前 MVP 由案例入库管理、元数据管理、智能标签管理和案例智能检索四个模块组成，覆盖文件接入与质量门禁、标准维护、标签演进和案例使用主链路。案例主检索已通过项目内 Vite 服务端代理接入 Dify Workflow；新增治理页面使用本地 Mock 数据，不接入数据库、权限、文书解析服务或其他真实业务接口。

页面尽量复用现有 `case-library-ai` 的公共顶栏、左侧功能菜单、业务目录、标准工具栏、表格、分页和全页面表单表达方式，并针对湖南需求调整模块名称、页面内容和数据来源。

## 2. 功能范围

### 2.1 案例检索

- 作为案例库默认入口，支持输入文号、专有名词、单位名称或自然语言问题描述。
- 检索首页主标题只显示“案例智能检索”，不使用图标和副标题说明。
- 已确认视觉方案：标题使用自然中文排版；主搜索框与搜索按钮采用圆润一体式胶囊结构；检索说明收敛为推荐词末尾的轻量信息图标，通过就近浮层按需展开，不再孤立占据行尾。该方案已沉淀为同类智能检索页的局部基准。
- 结果页采用“单一命令栏 + 连续结果册”结构：返回、检索框、结果数量和排序位于同一行，页面不再设置独立顶部搜索区或重复结果标题区。检索框中的查询内容即当前检索条件，不在页面其他位置重复展示。结果数量通过数字强调表达，排序直接使用“相关度优先 / 最新时间 / 最早时间”选项，不再重复显示“排序”标签。
- 结果页搜索框复用首页检索框的视觉语言，作为紧凑版本使用白色胶囊输入面、蓝色圆润按钮和同源阴影；检索按钮收敛为 `64px` 宽，并与胶囊右边缘保留 `8px` 内间距。命令栏本身保持透明，不再额外套白色底板。筛选和排序下拉框隐藏浏览器原生箭头，使用右侧内缩的统一细线箭头。
- 筛选面板与命令栏统一为 `8px` 圆角并对齐顶线；结果项相关度使用直角分隔信息列，不使用大圆角色块。
- 检索结果使用一张连续白色结果册承载，通过行间弱分隔和统一节奏表达层级，不再把每条结果做成独立悬浮卡片。
- “深度分析”和“查看详情”并入每条结果的标题行右侧，不设置独立操作栏；不单独显示原文预览图标，原文统一从案例详情进入。
- 结果页采用连续滚动浏览，不展示分页控件；结果册在最后一条数据后直接收底，不保留页脚空白，并与左侧筛选面板保持同一内容区底部节奏。
- 结果页主体使用等高白色双工作区：左侧筛选面板和右侧结果册都铺满可用内容高度。数据不足一屏时，剩余空间保持为所属工作区的白色阅读面，不露出大块灰色页面画布；数据超出时仅结果册内部滚动。
- 筛选面板支持收起与展开；收起后保留窄图标栏作为恢复入口，右侧结果区自动扩展占用释放宽度。
- 检索首页展示检索示例、最近检索和当前可检索文书范围，不使用无真实依据的热门排行。
- 检索结果页保留检索框，主检索同时覆盖文号、文书标题、相关单位和自然语言问题描述。
- 左侧常驻筛选与知识库元数据保持对应，提供年度、文书类型、监督领域、违规类型、文号和相关单位。其中监督领域使用约定类别单选，违规类型作为可搜索多选条件。
- 年度、文书类型、监督领域、违规类型、处理方式等可选值不在页面写死，由湖南知识库当前文书的 `doc_metadata` 动态汇总；相关单位和政策依据提供知识库现有值建议，同时保留关键词输入能力。
- “更多筛选”按需展开正式发文日期范围、处理方式和政策依据：处理方式使用可搜索多选，政策依据使用文件名称关键词，避免将高基数字段做成长下拉列表。
- 文书标题由主检索覆盖，不重复设置独立筛选项；年度与发文日期分开表达，不再使用含义模糊的“年度 / 日期”标签。
- 元数据值无法识别时保持为空，不在原型中强制归入“其他”类别。
- 结果页继续提供相关度、时间排序演示。
- 结果使用 Dify Workflow 返回的 TopK 相关案例，展示标题、文号、文书类型、日期、相关单位、命中片段和结构化案例要素。
- `score` 按“原始分值 × 100”转换为两位小数的相关度百分比，例如 `0.0927` 展示为 `9.27%`；该值仅表达检索排序相关度，不代表准确率或概率。
- 检索阶段由 Dify Workflow 按“Embedding + Hybrid + Rerank”链路返回备选案例；列表页与详情页对查询词及包含查询词的结构化案例要素短语进行一致高亮，帮助用户快速定位当前结果的直接命中依据，不自行推导或虚构语义匹配原因。
- 每条备选案例保留“深度分析”入口位置，本轮暂不调用 LLM；接口返回的 `hit_chunks` 保留在前端数据模型中，为后续分析“为什么相似、共同问题、关键差异、是否值得参考”提供输入。
- 深度分析采用单块嵌入式浅色分析带承载，结论区突出参考价值和建议，并提供可定位的原文分析依据；同一时刻只展开一条结果，避免破坏列表扫描效率。
- 深度分析的重新生成和评价属于后续设计；本轮实际可操作的是独立检索反馈，不冒充已连接分析 Workflow。
- 支持从结果进入案例详情，本轮展示真实检索元数据、命中摘要、结构化案例要素和本次结果中的其他相似案例。
- 完整正文、源文件附件和 OA 来源需要后续接口提供，本轮以明确的未接入状态展示，不继续使用 Mock 内容冒充真实数据。
- 本期不展示面向全部检索结果的生成式汇总答案；后续仅对用户主动选择的单条备选案例提供可选深度分析。

### 2.2 案例入库管理

- 统一承接 OA 同步文书和用户自主上传文件，不再把 OA 之外的文件排除在治理流程之外。
- 顶部状态收口为“已入库、未入库、全部”，默认进入未入库以承接当前工作；系统处理中、待人工处理和处理失败统一归入未入库，并在表格行内展示具体状态。“全部”固定放在最后。
- 左侧按文书类型筛选案例；一个案例只计一次。监督领域、方面、类型和性质属于问题级属性，不作为案例的唯一分类。
- 主页面复用“状态页签—文书类型目录—查询工具栏—业务表格—分页”。同一数据源计算页签、目录与列表数量。列表显示文书名称、文号、文书类型、主体名称、涉及问题数量、发文年度、所属检查名称、状态和接入时间；悬停问题数量可查看多项问题概述。
- 行操作统一为“处理 / 详情”：待人工处理和处理失败进入处理页，系统处理中和已入库进入详情页；取消“案例”“重试”“查看详情”等不一致入口。点击标题与行操作进入同一全页面详情或处理表单。
- “数据质量”不再作为独立菜单和第二套任务列表，而是案例入库的正式门禁：质量校验通过才进入“已入库”和正式知识库；解析失败、字段缺失、字段冲突、低置信度等阻断项统一留在“未入库”。悬停“待人工处理”状态可查看具体原因，避免用户无目的打开任务。
- 完整元数据超过标准抽屉的承载能力，入库详情和人工处理统一改用项目标准全页面表单。页面按“质量校验—文书基本信息—主体信息—问题认定—处理决定—来源与治理信息”连续组织，使用 64px 页头、四列字段栅格和必要弱分隔，不再使用右侧抽屉。
- 文书基本信息包含文书名称、文号、文书类型、发文年度、发文日期、所属检查年度、所属检查名称。主体信息独立成节，按“主体类型—个人/单位类型—名称”展示；`related_unit` 仅兼容主要主体名称汇总，不重复编辑。
- 一份文书包含多个问题；每项分别维护监督领域、方面、问题类型、问题性质（四列），以及问题事实、违规依据和证据。四川认定标准仅作参考，湖南正式标准待确认；问题级责任角色保留历史数据，当前表单不重复展示主体信息。
- 一个综合决定下支持多项措施，默认按文书类型展示处理或处罚目录，同时允许处罚文书中的整改措施。每项保留类别、类型、对象、金额/期限/证书号、具体内容；依据及原文明示的问题关联单独维护。旧多组决定数据保留，新录入不默认新增多个决定组。
- `problem_nature` 是基础认定标准中的问题性质，处罚阶次是执法裁量结论，两者不得互相替代。当前 MVP 暂不展示 `impact_level` 及影响度适用标准，待形成正式可核验的业务口径后再纳入详情和质量校验。
- 完整的主体、问题和处置数组保存在业务数据中；Dify 知识库元数据可保留面向筛选、统计和召回的聚合值，但不得用聚合字符串替代完整结构。来源与版本区展示接入来源、来源标识、源文件、入库状态、当前版本和更新时间，历史修改通过版本记录查看。
- 固定后台处理链路不在列表首屏常驻展示说明横条；流程说明进入设计文档，页面只展示用户可判断、可操作的业务状态。
- 正常数据自动入库是后续接入目标。本轮未入库数据可保存处理草稿；字段旁直接选择已有值或打开同一套标签建议处理面板，无须跳转后重填。标签管理承担集中维护，不产生第二份候选。固定目录疑问记录为元数据规则反馈。非必填标签允许留空后补，候选不自动成为正式值。
- 详情页的识别主线固定为“发现了什么问题—依据什么认定—最终如何处置”，优先保证问题、依据和决定之间可追溯；不通过堆叠卡片或重复字段制造层级。
- 数量表达根据数据量自适应：单项不显示“1”，也不显示“问题 1”“处置组 1”等开发式编号；2—5 项使用“共 N 项”和连续问题分组；超过 5 项的问题目录留待大量数据样例确认。具体事实、依据等明细只有多条时才显示数量。
- 问题概述与标准问题类型分开：详情用问题概述作为分组标题；编辑用问题概述输入框，不重复展示同一标题。violation_type 是可筛选、可治理的标准分类。
- 问题处理区按“问题概述与具体事实 → 分类认定与适用标准 → 违规依据与证据材料”组织。单问题编辑不增加“问题信息”标题；多问题保留连续编号。认定状态使用紧凑标签，不能拉伸为整行色带；分类字段沿用四列栅格并顶端对齐。
- 上传弹窗支持点击、多文件选择与拖入，展示文件名、大小、格式/大小校验结果，支持继续添加、移除。空文件、不支持格式或超过50MB的文件阻止提交。接收只生成本地未入库记录，绝不模拟解析完成。
- 处理页顶部汇总原有质量异常、必填缺失、目录未匹配与候选标签；条目可定位对应字段或异常处理结论。阻断项红色、可后补候选橙色；填入处理结论仅表示待校验，不自动发布。解析中的记录为只读等待态。
- 问题支持补充、收起/展开和确认移除，空事实与待确认认定产生阻断。人工核对分类后显示“人工确认”，不冒充模型匹配；仍执行正式目录值校验。本轮不新增真实标准检索接口。
- 处理决定支持多组、多措施和多条依据，按组勾选关联问题。移除问题同步清除关联；没有关联时明确为“整体处理 / 原文未明确对应问题”。处理内容单独占整行，处罚阶次按需展开，不再挤占通用字段首行。
- 尚有候选绑定的数组暂不允许移除条目，先处理候选再移除，避免索引式绑定错位；后续生产实现改用稳定的问题/措施ID绑定。移除仅修改草稿，正式数据仍需校验发布。
- 标签字段直接显示建议名称和待确认/退回状态。建议抽屉先给出建议说明、原文依据、同字段已有值，再按需展开新增定义；“采用现有标签并返回”“新增并用于当前字段”“仅保存建议”区别明确，候选与集中标签管理共用一份数据。
- 正常匹配字段不常驻显示“建议新增”或“标准目录有疑问”。可扩展目录的新增入口收进选择框末尾；已有候选或未匹配值才显示字段级处理提示。每个问题仅保留一个“反馈目录问题”入口，记录本问题分类上下文并定位元数据管理，保存、候选确认与入库边界不变。
- 已入库案例提供“申请复核”入口。用户可以针对文书字段、关联主体、问题认定、认定依据、处理决定、源文件或重复数据提交异议、建议修正和佐证；提交后生成独立复核任务，正式案例继续按当前版本提供检索，不允许直接覆盖正式数据。
- 复核通过后生成新版本，重新执行质量校验和知识索引，并保留修改前后值、申请人、审核人、依据和处理时间；复核驳回时保留结论。单条反馈优先修正当前案例，同类反馈聚合后用于评估抽取提示词、字段规则、标签目录和置信度阈值，不自动训练模型或直接修改治理规则。

### 2.3 元数据管理

- 面向实施人员或获授权的业务用户，负责定义“提取什么、属于哪个对象、怎样取值和校验”；不在本页维护另一套标签分类或逐条修改案例数据。
- 第一轮按入库详情的“文书基本信息、关联主体、问题认定、处理决定”组织 26 个业务字段。补齐标题、年度、方面、问题性质、责任主体、事实、依据及多主体/多处置关联；移除与最新认定层级重复的 `problem_domain`。候选标签、审核过程和更新时间等系统运行信息不作为 LLM 业务抽取字段。
- 数据类型只表达文本、长文本、整数等格式；“标签”不作为数据类型。取值方式独立表达固定目录、可扩展目录、原文提取、格式约束或系统关联。
- 监督领域复用入库页现有 13 个板块；方面、问题类型、问题性质和责任主体引用基础认定标准。标准约束字段不允许模型自动新增正式值，未匹配时保留原始事实并转待确认；问题性质和责任主体不能仅凭命中标准就机械赋值。
- 单值/多值以“当前对象”为边界：每个问题单独关联监督领域、方面、问题类型等，文书可有多个问题；业务库保留完整关联结构，知识库只按需生成筛选聚合值，二者不混为一套扁平字段。
- 分类字段自身作为标签类型入口，正式值、别名和候选值由该字段对应的目录管理；本页只展示取值来源、约束和只读样例。固定目录与可扩展目录均可引用目录，但新增值的权限规则不同，不要求用户重复创建同名类型。
- 保留已确认列表骨架：全宽状态页签“已生效、待生效、已停用、全部”（默认全部）、可收起的字段目录、标准查询工具栏、蓝灰表格和简版分页。页签数量统计全部配置，目录数量按当前页签计算，表格再叠加目录与查询条件；切换页签重置目录。去掉无样本依据的覆盖率、无业务用途的勾选框和常驻技术说明条。
- 列表展示名称、编码、所属对象、类型、取值数量、取值方式、取值来源和状态；保留“详情 / 编辑”两项行操作。查看为只读文本，编辑可修改名称、业务定义、抽取匹配规则、应用位置和两个使用开关；已有字段编码、所属对象、格式与取值方式暂不开放直接修改，防止绕过后续变更影响确认。
- 新增及保存草稿、查询、目录搜索、状态筛选、分页和导出均使用本地配置数据；已发布字段修改后保留原配置，单独保存修改草稿并进入待发布。新增分类字段仅创建字段草稿，不假装目录或标签管理已完成联动。
- 本轮不实现版本发布、认定标准导入、真实标签目录联动、影响分析或存量回填。发布入口明确处于未接入状态，不显示虚假的成功提示；后续确认后再接 Dify 和服务端。页面配置状态、字段样例均为演示配置，不代表 Dify 现场已完成对应升级。

### 2.4 智能标签管理

- 左侧树直接取元数据中已生效且启用标签维度的字段，按相同对象分组；不独立维护“标签分类”。关闭字段标签开关后入口隐藏，已有值和引用保留。
- 状态与元数据统一为已生效、待生效、已停用、全部。待生效明细显示草稿、待确认或已退回。所有数量和案例引用从同一份会话数据计算，不使用固定统计数字。
- 可扩展目录支持保存建议、确认新增、采用现有正式标签和退回。新增校验同字段名称/别名重复，但不声称已完成语义去重；人工仍须比较现有值。
- 固定目录禁止自由新增；入口引导核对标准并留下规则反馈。正式标签本轮只编辑定义和别名、停用或重新启用；重命名、拆分合并的版本迁移后续完善。
- 候选按案例ID和字段路径关联：确认/采用已有值后更新未入库处理数据，仍需校验才能入库；退回同步原因。已入库案例不被候选处理覆盖。
- 当前用户有直接确认权限，不等待累计20条或另一角色；集中反馈分析与单条候选处理分开。

### 2.5 既有扩展模块（当前 MVP 隐藏）

- 案例档案、案例智能分析和典型案例管理的早期演示代码暂时保留，但不进入本期湖南菜单。
- 认定标准管理、存量回填任务和真实审批流作为后续阶段能力，不在第一版页面中单独铺开。

## 4. 数据与交互

- 案例检索通过同源 `POST /api/hunan-case-search` 调用项目内服务端代理，由代理向 Dify `POST /v1/workflows/run` 发起 blocking 请求。
- 筛选选项通过同源 `GET /api/hunan-case-search/filters` 获取；服务端使用知识库 API 读取当前数据集文书元数据，按字段去重、计数并缓存 5 分钟，知识库 API Key 与数据集 ID 不进入浏览器端。
- Dify API Key 仅从服务端环境变量 `DIFY_API_KEY` 读取，不使用 `VITE_` 前缀，不进入浏览器构建产物。
- 知识库元数据接口分别从服务端环境变量 `DIFY_KNOWLEDGE_API_KEY`、`DIFY_KNOWLEDGE_DATASET_ID` 读取授权与湖南数据集标识，同样不使用 `VITE_` 前缀。
- 服务端提取 `data.outputs.result` 并向页面返回 `{ total, results }`；兼容 Dify 输出为对象或 JSON 字符串。
- 检索页提供加载中、请求失败、无结果和重新检索状态；新的检索会中止前一次尚未完成的浏览器请求。
- 页面会校验同源检索接口是否返回 JSON；如果从未挂载湖南专用代理的旧预览地址打开，不再显示晦涩的解析错误，而是明确提示改用已启动的 51729 演示地址。
- 左侧功能菜单支持展开态和收起态，并通过 `feature` 查询参数记录当前模块。
- 管理页使用 governanceModel.ts 共享会话状态，增改、草稿、生效及版本记录在本地联动；刷新恢复初始数据。文件选择只保留本地预览对象，不发送服务器，也不冒充解析完成。
- 主检索词调用真实 Dify Workflow；结果页的时间排序只对本次返回结果进行前端排序。
- 当前 Dify Workflow 仍只接受 `query`；服务端代理在 Workflow 返回候选后按同一套结构化元数据执行年度、文书类型、监督领域、违规类型、文号、相关单位、发文日期、处理方式和政策依据过滤。当前知识库 9 份文书且 Workflow TopK 为 10，能够覆盖现阶段候选；数据量超过 TopK 后，应把筛选条件前置为 Workflow 输入并在知识检索节点执行元数据过滤。
- 检索结果增加反馈入口，记录检索词、文书ID、片段、反馈类型和说明到本地统一反馈记录；不会改变真实检索规则。长片段默认三行，可展开。深度分析仍禁用，保留 hit_chunks，不调用分析 Workflow。
- 案例入库管理、元数据管理和智能标签管理使用湖南省财政监督场景本地 Mock 数据；上传、同步、筛选、选中、详情切换、批量处理、版本发布和审核决定只提供静态交互反馈，不调用真实治理接口。
- 入库 Mock 数据包含单问题和三问题两种文书形态，并提供已入库案例发起复核、复核中状态和查看复核任务的静态交互，用于验证数量自适应和版本化纠错流程。
- 当前已发布入库 Workflow 仍只抽取原有 10 个元数据字段，尚未覆盖关联主体数组、问题数组、具体问题事实、问题性质、责任主体、问题级认定标准，以及处置组和问题之间的关联。当前页面表达目标数据模型；进入真实联调前需同步升级 LLM 结构化输出、业务数据存储和写入知识库 Metadata 的聚合转换逻辑。
- 目标流程中无阻断项可自动入库；必填未确认值阻断，可选未确认值留空后补。原型不模拟后台自动完成，以人工校验按钮演示最终门禁。
- Axure 变量暴露当前 `feature_key` 和 `feature_name`。

- 案例检索详情页使用连续白色业务页面：顶部操作栏、案例摘要和三栏正文在同一阅读面内自然接续，不再拆成多张悬浮卡片；栏间仅用留白和弱分隔线组织，选中项、命中片段、匹配标签和文书纸张保留必要浅底或边界。
- 案例检索详情页的页头只显示“案例详情”，不重复文号和文书类型；案例标题与完整元数据只在摘要区出现。内容定位已表达当前查看范围时，正文区不再重复显示“命中内容 / 文书正文 / 源文件附件”标题栏。分隔线按三级层级使用：摘要与核验阅读区之间使用全宽弱横线表达主阶段切换；三栏之间使用上下留白、末端渐隐的短竖线建立阅读列；右侧两个辅助分组之间使用缩进渐隐短横线。不同层级在线长、方向和透明度上必须有区别，不能全部删除，也不能全部画成贯穿边框。
- 案例检索三页遵循信息层级优先、边界克制：普通分组、摘要、结果项和侧栏先通过留白、浅底和文字层级建立结构，再按业务阶段、阅读列、局部分组和独立载体补充不同权重的边界；不以线条或卡片数量作为独立优化指标。
- 案例入库详情和数据处理页采用标准全页面四列表单；全部正式元数据在表单中完整展开，源文件作为页头动作按需查看，不使用过宽抽屉承载完整字段。
- 分析页面使用轻量指标带、扁平列表和浅色信息分组，不使用营销页式大卡片。
- 三个治理页面按已确认业务列表页强基准实现：48px 状态页签、250px 业务目录、56px 标准查询工具栏、蓝灰标准表格和简版分页；不设置重复页面标题块、统计卡片墙或自定义三栏工作台。
- 元数据和智能标签的局部维护仍可使用标准右侧抽屉；案例入库的完整元数据与质量问题因字段量和认定依据较多，使用全页面表单，不强行套用抽屉。
