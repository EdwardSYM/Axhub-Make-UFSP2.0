# 通用知识入库治理与智能检索整体流程说明

## 一、为什么需要这套整体框架

当前需要处理的不只是“把文件放进知识库”，而是把不同地区、不同来源、不同格式的数据，转成可检索、可分类、可解释、可持续更新的知识资产。

如果只有单次 LLM 抽取或单个入库 Workflow，会产生几个长期问题：

- 不同项目的字段、标签和分类口径容易混用。
- LLM 可能生成同义、近义或不稳定的新标签。
- 元数据或认定标准调整后，历史数据无法自动补充和迁移。
- 检索只能返回“相似结果”，难以解释为什么命中、依据是什么。
- 所有异常都依赖人工逐条处理，会增加用户工作量。

因此，整体方案需要同时覆盖四件事：

1. 新数据标准化入库。
2. 元数据、标签和认定标准治理。
3. 存量数据回填与版本迁移。
4. 智能检索、可选深度分析和用户反馈回流。

## 二、总体设计思路

整体采用“通用引擎 + 项目配置”的方式：

- 通用引擎负责文件解析、切块、LLM 调用、规则校验、审核分流、知识库写入、检索和回填。
- 项目配置负责定义湖南、甘肃等不同项目各自的元数据 Schema、正式标签、认定标准、Prompt、切块策略、阈值和审核规则。
- Workflow 负责编排稳定流程；LLM 负责理解非结构化内容；确定性规则负责正式值、格式、别名和版本校验。
- 正常且高置信度的数据自动处理；只有新标签、低置信度、冲突值和规则升级差异进入人工审核。

### 2.1 一张图看懂这套方案

```mermaid
flowchart LR
    A[不同来源文件\nWord · PDF · Excel] --> B[按项目加载配置\n湖南 / 甘肃 / 其他]
    B --> C[解析与切块\n保留原文位置]
    C --> D[LLM 提取事实\n规则匹配正式值]
    D --> E{是否可以自动确认}
    E -->|高置信度且规则通过| F[写入案例知识库]
    E -->|新标签 / 冲突 / 低置信度| G[治理工作台审核]
    G --> H[发布标签或规则新版本]
    H --> F
    H --> I[影响分析与历史回填]
    I --> F
    F --> J[Embedding + Hybrid + Rerank]
    J --> K[快速返回候选案例]
    K --> L{用户是否需要进一步判断}
    L -->|否| M[查看详情或结束]
    L -->|是| N[按需调用 LLM 深度分析]
    N --> O[依据、差异、参考价值]
    O --> P[用户反馈]
    P --> G
```

这不是一个“让 LLM 自动决定一切”的系统，而是一条可控制的知识生产线：

- 配置决定每个项目使用什么字段、标签、Prompt、切块方式和审核阈值。
- Workflow 按固定步骤执行文件处理、异常分流、检索和回填。
- LLM 只处理需要理解语义的环节，并必须返回原文依据。
- 治理人员只处理少量异常，不逐条审核所有正常数据。
- 当前正式结果进入知识库；候选值、审核记录和版本历史保存在治理数据中。

### 2.2 什么人使用什么功能

| 使用角色 | 主要目标 | 直接使用的功能 | 不需要接触的内容 |
|---|---|---|---|
| 业务使用人员 | 快速找到可参考案例并判断是否有用 | 案例检索、筛选、详情、按需深度分析、结果反馈 | Workflow 节点、模型参数、标签版本 |
| 业务专家 / 治理审核人员 | 维护业务口径并处理系统无法自动确认的少量异常 | 候选标签审核、冲突值修正、标准确认、反馈处理 | API Key、知识库接口、部署参数 |
| 知识库管理员 | 保证字段、标签、版本和历史数据一致 | 元数据定义、标签目录、规则发布、影响分析、回填任务 | 逐条业务检索过程 |
| 项目实施 / 技术管理员 | 配置不同项目的处理能力并保障运行 | 项目配置、Prompt、Dify Workflow、接口、日志、阈值和评测集 | 代替业务专家决定正式业务口径 |

### 2.3 按阶段理解：谁做什么、最后得到什么

| 阶段 | 业务人员看到什么 | 系统在后台做什么 | 主要产出 |
|---|---|---|---|
| 1. 项目初始化 | 确认湖南项目使用的字段、标签和业务口径 | 建立独立 `project_id`，装载 Schema、Prompt、切块、阈值和 Workflow 配置 | 湖南项目配置基线 |
| 2. 文件入库 | 上传文件并查看处理状态 | 解析文件、切块、LLM 抽取事实、保留原文位置 | 原始字段、候选分类和依据 |
| 3. 标准化治理 | 只处理待审核异常 | 正式值匹配、别名归一、冲突检查和置信分流 | 当前有效元数据、正式标签或治理任务 |
| 4. 规则发布与回填 | 查看变更影响并决定是否执行 | 生成新版本、筛选受影响文档、增量重跑 | 新旧差异、回填结果和版本记录 |
| 5. 智能检索 | 输入问题、筛选并查看候选案例 | Embedding、全文检索、融合/Rerank、文档聚合 | 候选案例、命中片段和排序依据 |
| 6. 深度分析 | 点击单条案例进一步判断 | 获取全文、命中片段和认定标准，按需调用 LLM | 相似原因、差异、参考价值和证据 |
| 7. 反馈优化 | 对错误结果修正或评价 | 聚合相似反馈，形成文档修正、规则调整或检索评测任务 | 可审核的优化建议和持续改进数据 |

每个阶段都应先输出结构化结果，再决定是否进入下一阶段。这样某个 LLM、知识库或 Workflow 将来替换时，不会破坏整条业务链。

### 2.4 配置化与代码化的边界

MVP 优先通过配置实现，但不能让页面和数据结构直接绑定 Dify。推荐边界如下：

| 层级 | MVP 主要实现方式 | 后续生产化方式 | 稳定边界 |
|---|---|---|---|
| 页面 | 项目现有 React 原型与管理页面 | 继续复用或迁移到正式前端 | 页面只调用统一业务 API |
| 接口层 | 项目 BFF 统一封装 Dify 和知识库接口 | 正式后端服务 | 请求和响应结构保持稳定 |
| 流程编排 | Dify Workflow 配置节点、分支和 LLM 调用 | 可逐步改为代码工作流或任务服务 | Workflow 输入输出协议不变 |
| 规则与配置 | 项目配置文件或轻量治理库 | 数据库中的配置中心、版本中心 | 使用 `project_id + config_version` 隔离 |
| 文档知识 | Dify 知识库存原文、切块和当前有效元数据 | 可替换为正式检索引擎与对象存储 | `document_id`、chunk、元数据字段保持可迁移 |
| 候选与审核 | 轻量治理数据表 | 正式治理数据库和审计日志 | 不把候选值直接写成正式知识库元数据 |

因此，Dify 在 MVP 中是“可配置的执行器”，不是产品唯一底座。未来把 Dify 节点替换为代码服务时，页面、业务概念和治理数据不需要重做。

## 三、从来源数据到检索反馈的完整时序图

```mermaid
sequenceDiagram
    autonumber
    participant SRC as 来源数据
    participant IW as 入库治理 Workflow
    participant CFG as 项目配置与规则中心
    participant AI as LLM
    participant GOV as 治理审核工作台
    participant STD as 认定标准库
    participant KB as 案例知识库
    participant SW as 检索/分析 Workflow
    participant RET as Embedding·Hybrid·Rerank
    actor USER as 业务用户

    Note over SRC,USER: 阶段一：识别数据来源并加载对应项目规则
    SRC->>IW: 上传 Word / PDF / Excel<br/>携带 project_id、source_type
    IW->>CFG: 获取项目配置
    CFG-->>IW: 元数据 Schema、正式标签、别名<br/>认定标准、Prompt、切块策略、阈值、规则版本

    alt 案例文书、问题线索或业务资料
        Note over IW,AI: 阶段二A：案例类数据解析、切块和 AI 抽取
        IW->>IW: 文件解析、版面识别、业务段落切块<br/>保留文件名、页码、段落和上下文位置
        IW->>AI: 原文/切块 + 字段定义 + 候选标签范围
        AI-->>IW: 原始字段、候选分类、原文依据、置信说明

        opt 需要依据制度或认定标准分类
            IW->>STD: 按问题事实检索相关标准
            STD-->>IW: 标准名称、规则条目、来源文件与位置
            IW->>AI: 问题事实 + 候选标准
            AI-->>IW: 分类判断、适用标准及依据
        end

        Note over IW,CFG: 阶段三：确定性规则优先，AI 只辅助理解和候选判断
        par 固定值或枚举字段
            IW->>CFG: 按编码、正式名称和别名精确匹配
        and 可扩充标签字段
            IW->>CFG: 优先匹配正式标签，未匹配值转为候选
        and 开放字段
            IW->>IW: 按原文提取并进行格式规范、去重和别名归一
        end
        CFG-->>IW: 正式值、候选值、冲突项、校验结果和规则版本

        alt 高置信度且通过规则校验
            IW->>KB: 写入原文、切块、正式元数据、正式标签<br/>判断依据、来源位置和规则版本
        else 新标签、低置信度、冲突值或无法归类
            IW->>GOV: 创建待审核任务<br/>附候选值、相似正式标签、原文依据和建议
            GOV-->>USER: 推送需要人工判断的少量异常
            USER->>GOV: 批准 / 合并 / 改名 / 驳回 / 修正

            alt 批准为新正式标签
                GOV->>CFG: 新增正式标签并发布新规则版本
            else 合并、改名或维护别名
                GOV->>CFG: 更新别名、合并关系和迁移规则
            else 驳回候选
                GOV->>GOV: 保留审核记录，不写入正式标签库
            end

            GOV-->>IW: 返回最终审核结论
            IW->>KB: 写入修正后的正式结果并保留审核依据
        end

    else 认定标准、制度政策或 Excel 规则表
        Note over IW,STD: 阶段二B：标准类数据单独进入认定标准库
        IW->>IW: 解析文件、Sheet、表头、规则行和层级关系
        IW->>AI: 提取板块、方面、问题类型、表现形式<br/>问题性质、责任主体、适用条件等结构化规则
        AI-->>IW: 标准候选结构 + 原始文件位置
        IW->>GOV: 提交标准审核任务
        GOV-->>USER: 展示结构化结果与原表依据
        USER->>GOV: 确认、修正或驳回
        GOV->>STD: 写入正式标准、来源位置和版本
    end

    opt 元数据 Schema、标签或认定标准发生新增、修改、合并或停用
        Note over GOV,KB: 阶段四：识别受影响历史数据并增量回填
        GOV->>IW: 发布治理变更和影响范围
        loop 每一条受影响的历史文档
            IW->>KB: 读取原文、已有切块、旧元数据和旧规则版本
            IW->>AI: 按最新字段和标准重新抽取或分类
            AI-->>IW: 新结果、依据和置信说明
            IW->>CFG: 使用最新规则校验
            CFG-->>IW: 正式结果和新规则版本
            IW->>KB: 更新元数据/标签<br/>保留新旧差异、更新时间和审核状态
        end
    end

    Note over KB,USER: 阶段五：真实检索流程
    USER->>SW: 输入自然语言问题 + 可选筛选条件
    SW->>CFG: 获取当前项目可用筛选值、检索配置和质量阈值
    CFG-->>SW: 年度、文书类型、监督领域、问题分类等正式值
    SW->>RET: query + metadata filters
    RET->>KB: Embedding 向量检索 + 关键词全文检索
    KB-->>RET: 候选文档、document_id、hit_chunks<br/>元数据和初始检索分

    alt 使用权重融合
        RET->>RET: 按语义权重和关键词权重合并排序
    else 使用 Rerank 模型
        RET->>RET: 用 query 对候选片段重新相关性排序
    end

    RET-->>SW: 排序后的候选结果和排序分
    SW->>SW: 文档聚合、去重、最低质量过滤<br/>异常命中片段过滤和结果解释整理
    SW-->>USER: 返回案例列表、相关度档位、命中片段<br/>匹配原因和可追溯依据

    opt 用户点击“深度分析”
        Note over SW,AI: 深度分析按需调用，不对所有结果全局执行
        USER->>SW: query + document_id + hit_chunks
        SW->>KB: 获取文书全文、完整元数据、相关切块和源文件索引
        KB-->>SW: 文档上下文
        SW->>STD: 检索相关认定标准和政策依据
        STD-->>SW: 标准条目及来源位置
        SW->>AI: 查询意图 + 当前案例 + 命中片段 + 标准依据
        AI-->>SW: 为什么相似、共同问题、主要差异<br/>是否值得参考及证据位置
        SW-->>USER: 展示结构化深度分析结果
    end

    opt 用户对搜索、分类或深度分析结果反馈
        USER->>GOV: 正向/负向反馈、修正值和补充说明
        GOV->>GOV: 形成待治理任务并累计质量数据
        GOV->>CFG: 审核后调整别名、标签、标准、阈值或规则版本
        Note over CFG,SW: 新规则从后续请求生效；必要时触发历史数据回填
    end

    Note over IW,SW: 当前以 Workflow + LLM + 规则校验为主，不必引入 Agent。<br/>未来只有跨多个知识库、反复检索、动态选择工具并依据中间结果调整计划时，再增加 Agent 编排层。
```

## 四、分阶段时序图

### 阶段一：来源识别与项目配置路由

本阶段先确定数据属于哪个项目和哪种来源，再加载该项目自己的元数据、标签、Prompt 和处理规则。湖南、甘肃等项目之间不共用业务规则，只复用处理引擎。

```mermaid
sequenceDiagram
    autonumber
    participant SRC as 来源数据
    participant IW as 入库治理 Workflow
    participant CFG as 项目配置与规则中心

    SRC->>IW: 上传文件 + project_id + source_type
    IW->>CFG: 查询项目配置和当前规则版本

    alt 项目配置存在
        CFG-->>IW: 返回 Schema、标签、Prompt<br/>切块策略、阈值和审核规则
        IW->>IW: 创建本项目独立处理上下文
    else 项目未配置或来源类型不支持
        CFG-->>IW: 返回未配置状态
        IW-->>SRC: 停止处理并提示补充配置
    end

    Note over IW,CFG: 不得自动回退到其他地区的配置，避免知识库和业务口径串用
```

### 阶段二：文件解析、切块与 AI 抽取

本阶段根据来源类型分为“案例类数据”和“标准类数据”。两类数据使用不同的解析与入库路径。

```mermaid
sequenceDiagram
    autonumber
    participant IW as 入库治理 Workflow
    participant PARSE as 文件解析与切块
    participant AI as LLM
    participant STD as 认定标准库
    participant GOV as 治理审核工作台
    actor USER as 业务审核人员

    alt 案例文书、问题线索或业务资料
        IW->>PARSE: 解析 Word / PDF / Excel
        PARSE->>PARSE: 按业务段落切块并保留页码、段落和上下文
        PARSE-->>IW: 原文、结构化位置和 chunks
        IW->>AI: 原文/chunks + 字段定义 + 候选分类范围
        AI-->>IW: 原始字段、候选标签、依据和置信说明

        opt 需要依据认定标准分类
            IW->>STD: 检索相关标准条目
            STD-->>IW: 标准内容、名称和来源位置
            IW->>AI: 问题事实 + 候选标准
            AI-->>IW: 分类建议、适用标准和判断依据
        end

    else 认定标准、制度政策或 Excel 规则表
        IW->>PARSE: 解析文件、Sheet、表头和规则行
        PARSE-->>IW: 层级关系、单元格内容和来源位置
        IW->>AI: 按标准 Schema 提取结构化规则
        AI-->>IW: 板块、问题类型、表现形式<br/>适用条件、责任主体等候选结果
        IW->>GOV: 创建标准审核任务
        GOV-->>USER: 展示结构化结果与原文件位置
        USER-->>GOV: 确认、修改或驳回
    end
```

### 阶段三：元数据标准化、标签匹配与审核分流

本阶段决定哪些结果可以自动成为正式数据，哪些结果必须进入候选池和人工审核。

```mermaid
sequenceDiagram
    autonumber
    participant IW as 入库治理 Workflow
    participant CFG as 项目配置与规则中心
    participant GOV as 治理审核工作台
    participant KB as 案例知识库
    actor USER as 业务审核人员

    par 固定值或枚举字段
        IW->>CFG: 使用编码、正式名称和别名精确匹配
    and 可扩充标签字段
        IW->>CFG: 匹配正式标签并计算候选相似度
    and 开放字段
        IW->>IW: 原文提取、格式规范、去重和别名归一
    end

    CFG-->>IW: 正式值、候选值、冲突项<br/>校验状态和规则版本

    alt 高置信度且通过规则校验
        IW->>KB: 自动写入正式元数据、标签、依据和版本
    else 新标签、低置信度、冲突或无法归类
        IW->>GOV: 创建待审核任务
        GOV-->>USER: 展示候选、相似标签、原文依据和建议
        USER->>GOV: 审核决策

        alt 批准新增
            GOV->>CFG: 新增正式标签并发布新版本
        else 合并或改名
            GOV->>CFG: 更新正式值、别名和迁移关系
        else 驳回
            GOV->>GOV: 记录原因，不修改正式规则
        end

        GOV-->>IW: 返回最终正式值
        IW->>KB: 写入修正结果并保留审核记录
    end
```

### 阶段四：规则变更与历史数据回填

本阶段处理元数据字段新增、标签修改、认定标准升级以及旧值更新，不要求人工逐条修改历史文档。

```mermaid
sequenceDiagram
    autonumber
    participant GOV as 治理审核工作台
    participant CFG as 项目配置与规则中心
    participant IW as 回填 Workflow
    participant KB as 案例知识库
    participant AI as LLM

    GOV->>CFG: 发布 Schema / 标签 / 标准变更
    CFG-->>GOV: 生成新规则版本和生效范围
    GOV->>IW: 触发影响分析
    IW->>KB: 按字段、旧值、标签或标准版本筛选历史文档
    KB-->>IW: 返回受影响 document_id 列表

    loop 每一条受影响文档
        IW->>KB: 读取原文、chunks、旧元数据和旧版本
        opt 需要重新理解原文或重新分类
            IW->>AI: 使用最新字段和标准重新抽取
            AI-->>IW: 新结果、依据和置信说明
        end
        IW->>CFG: 使用最新正式值和规则校验
        CFG-->>IW: 新正式结果和规则版本
        IW->>KB: 更新元数据/标签<br/>保留新旧差异、更新时间和审核状态
    end

    IW-->>GOV: 返回处理数量、异常数量和差异报告
```

### 阶段五：智能检索、排序与结果解释

本阶段执行第一层快速检索。Embedding、全文检索和 Rerank 只负责召回与排序，不直接生成深度分析结论。

```mermaid
sequenceDiagram
    autonumber
    actor USER as 业务用户
    participant SW as 历史案例智能检索 Workflow
    participant CFG as 项目配置与规则中心
    participant RET as Embedding·Hybrid·Rerank
    participant KB as 案例知识库

    USER->>SW: 自然语言 query + 可选筛选条件
    SW->>CFG: 获取本项目筛选值、Top K 和质量阈值
    CFG-->>SW: 正式元数据值和检索配置
    SW->>RET: query + metadata filters
    RET->>KB: 向量检索 + 关键词全文检索
    KB-->>RET: 候选 document_id、hit_chunks<br/>元数据和初始检索分

    alt 权重融合
        RET->>RET: 合并语义分与关键词分并排序
    else Rerank 模型
        RET->>RET: 对 query 和候选片段重新相关性排序
    end

    RET-->>SW: 排序候选和排序分
    SW->>SW: 文档聚合、去重、最低质量过滤<br/>异常片段过滤和命中原因整理
    SW-->>USER: 案例列表、相关度档位、命中片段和匹配依据

    Note over SW,USER: 排序分用于比较候选先后，不直接展示为准确率百分比
```

### 阶段六：按需深度分析

深度分析只在用户点击某一条结果后调用，避免对全部候选案例调用 LLM，控制响应时间和模型成本。

```mermaid
sequenceDiagram
    autonumber
    actor USER as 业务用户
    participant DW as 案例深度分析 Workflow
    participant KB as 案例知识库
    participant STD as 认定标准库
    participant AI as LLM

    USER->>DW: query + document_id + hit_chunks
    par 获取案例完整上下文
        DW->>KB: 获取全文、元数据、相关 chunks 和源文件索引
        KB-->>DW: 案例上下文
    and 获取判断依据
        DW->>STD: 检索相关标准和政策依据
        STD-->>DW: 标准条目及原始位置
    end

    DW->>AI: 查询意图 + 案例上下文 + 命中片段 + 标准依据
    AI-->>DW: 为什么相似、共同问题、主要差异<br/>是否值得参考及证据位置
    DW->>DW: 校验输出结构和证据引用
    DW-->>USER: 展示结构化分析和反馈入口
```

### 阶段七：用户反馈与持续优化

用户反馈先进入治理队列，不能未经审核直接修改正式标签、阈值或全局规则。

```mermaid
sequenceDiagram
    autonumber
    actor USER as 业务用户
    participant GOV as 治理审核工作台
    participant CFG as 项目配置与规则中心
    participant IW as 入库/回填 Workflow
    participant SW as 检索 Workflow
    participant KB as 案例知识库

    USER->>GOV: 正向/负向反馈、修正值和补充说明
    GOV->>GOV: 聚合相似反馈并形成待治理任务

    alt 单条文档抽取或分类错误
        GOV->>IW: 下发文档修正任务
        IW->>KB: 更新该文档正式结果并保留修订记录
    else 标签、元数据或认定标准存在系统性问题
        GOV->>CFG: 提交规则变更并审核发布
        CFG->>IW: 触发受影响历史数据回填
    else 检索排序或阈值问题
        GOV->>CFG: 形成检索配置调整候选
        CFG->>SW: 在评测集验证后发布新配置
    end

    GOV-->>USER: 返回反馈处理状态和最终结论
```

## 五、图中几个关键分支

### 1. 两类来源数据分开处理

- 案例文书、问题线索和业务资料进入案例知识库。
- 认定标准、制度政策和 Excel 规则表进入认定标准库。
- 两类数据可以互相引用，但不能混成同一种知识对象。

### 2. 三类元数据值采用不同处理方式

- 固定值或枚举字段：使用编码、正式名称、别名进行确定性匹配，例如行政区划。
- 可扩充标签字段：先匹配正式标签；匹配失败时进入候选池，经审核后才能成为正式标签，例如违规类型。
- 开放字段：按原文抽取和格式规范，不要求提前枚举所有值，例如标题、文号、单位名称和日期。

### 3. LLM 不能直接修改正式规则

LLM 负责抽取、理解、候选分类和依据整理。正式标签新增、标签合并、规则修改和标准发布必须经过规则校验或人工审核，避免模型结果直接污染正式数据。

### 4. 历史数据回填属于治理流程

当新增元数据字段、调整标签、更新认定标准或修改规则版本时，系统识别受影响文档并批量重跑，只更新受影响数据，同时保留新旧结果差异和规则版本。

### 5. 搜索和深度分析分两层

- 第一层检索使用 Embedding、全文检索、权重融合或 Rerank，快速返回候选案例。
- 第二层深度分析只在用户点击后调用 LLM，结合 `query`、`document_id`、`hit_chunks`、全文和认定标准生成分析。
- `hit_chunks` 是首次检索实际命中的文档片段，用于解释命中原因、定位原文并缩小深度分析上下文。

Dify 官方模型接口说明中，Rerank 用于在初始检索之后，根据查询与候选文档的相关性重新排序；它产生的是排序相关性分，不应直接解释为准确率概率：[Dify Rerank 官方说明](https://docs.dify.ai/zh/develop-plugin/features-and-specs/plugin-types/model-schema)。

## 六、建议拆分的 Workflow

| Workflow | 主要职责 | 是否调用 LLM |
|---|---|---|
| 通用入库治理 Workflow | 项目路由、解析切块、元数据抽取、规则校验、异常分流、知识库写入 | 是 |
| 元数据与标签治理 Workflow | 候选审核、标签合并、规则发布、影响范围识别、存量回填 | 按需 |
| 历史案例智能检索 Workflow | Embedding、Hybrid、Rerank、筛选、阈值过滤和结果整理 | 通常不需要生成式 LLM |
| 案例深度分析 Workflow | 按用户点击调用，解释相似性、共同问题、差异和参考价值 | 是 |

## 七、当前阶段与后续扩展边界

当前阶段先完成 Workflow、LLM、规则中心、治理工作台和知识库之间的稳定闭环，不需要为了“智能化”提前引入 Agent。

后续出现以下任务时，再考虑在现有 Workflow 上增加 Agent：

- 同一个问题需要跨多个知识库反复检索。
- 需要根据中间结果决定下一步调用哪个工具。
- 需要自动调整检索词、扩大或缩小范围并多轮验证。
- 需要综合案例、制度、指标和外部数据形成研究报告。

Agent 应作为上层动态编排能力，复用现有入库、检索、深度分析和治理 Workflow，而不是替代这些稳定流程。
